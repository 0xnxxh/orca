The whole design in one sentence

Who owns a shell is our business and lives on our disk. Whether a shell is alive is the host’s business and only the host may say it. Every bug in this area came from the client answering the second question by itself — from a timeout, a missing list entry, or the wording of an error message.

1 · The rule

This is what lets the offline case work without inventing an authority layer. Ownership is answerable while disconnected because it never depended on being connected. Fate simply isn’t answered by the client at all.

2 · One record instead of three

Today three durable records describe overlapping facts and can disagree in nine enumerated ways.

type PaneShellOwnership = {
  leafId: string          // PRIMARY KEY — the layout leaf's UUID
  hostId: ExecutionHostId // 'local' | 'ssh:<target>' | 'runtime:<id>'
  worktreeId: string
  ptyId: string           // one namespace, always
  incarnationId: string   // which process, not just which id
  relayInstanceId?: string// which relay PROCESS owned it
  state: 'attached' | 'detached' | 'terminated'
}
// deliberately absent: tabId, paneKey, any second record

Uniqueness is on (hostId, ptyId, incarnationId) — not ptyId alone, because relay ids are minted pty-1, pty-2… per relay process. After any relay restart, pty-1 exists again on every host. A collision isn’t unlikely here; it’s guaranteed.

3 · Why the key is the leaf, not the pane

This one choice deletes a whole class of bug rather than managing it.

The tab is location, and location changes. The leaf is identity, and it never does. Storing the tab means storing something that goes stale; deriving it means it is always current.

4 · Delete the identity check on attach

This is a live bug today

The relay compares the pane it recorded at spawn against the pane you claim now. After a detach they differ, so it refuses — with the words PTY "x" not found. The client reads “not found”, concludes the shell died, and starts a replacement with agent resume while the original keeps running.

The check is wrong in both directions, which is why the design deletes it rather than repairing it:

SituationWhat it doesWhat it should do
Live pane, moved to another tabRejects it — and the rejection reads as deathAttach normally
Relay restarted and recycled pty-3 for the same paneAccepts it — pane and tab both matchRefuse — different shell

It fails at its own stated purpose. The replacement is free: every successful attach already returns incarnationId, so comparing that catches the recycled-id case the identity check was written for, and never rejects a pane that merely moved.

5 · When may we start a replacement shell?

Only on positive proof. Two rows grant it; everything else does not.

Row 2 is the subtle one, and it’s sound without any timer. The relay’s shell table is a plain in-memory map, and entries are removed when a shell exits. So “the very process that created this shell no longer has it” is an observed exit. A restarted relay reports a different process id, and we correctly claim to know nothing.

And stop fabricating exits

Today a failed reattach sends the pane a synthetic exit code -1. That is a statement about a process we know nothing about. It’s removed, and the case routes into a non-destructive branch that already exists three lines above it — a branch collapse, not a new mechanism.

6 · Orphans are computed, never stored

A stored orphan list would go stale across exactly the disconnect during which the truth changed — and an orphan is only actionable while you’re connected anyway. Note the failure branch: a failed listing yields unknown, never “everything is an orphan”.

Killing is always an explicit, per-shell user action, with the working directory, title and pane shown. The design deletes the “is this shell owned by someone else?” classifier entirely — it was based on an id that is randomly generated per install, so it wrongly exempted your own shells after a repo re-add and wrongly included another device’s shells whenever two installs shared state.

7 · How a record ends

ExitWhenThe shell
RetireProven terminated, or you closed itGone — record deleted
ReleaseYou closed the pane or deleted the tabKept running — becomes an adoptable orphan, and can never authorize a replacement
Never“It wasn’t in the last list we saw”Absence is not an ending

Release fires only from explicit close and tab-delete events — never from noticing a leaf missing from a layout publish. During a detach there is a genuine window where no layout contains the leaf, and a save landing in that window would otherwise look exactly like a deliberate removal.

10 · Shipping order

Six steps, each its own change, each independently revertible.

The one deliberate trade

Row 3 is a real product change. Today an unprovable case silently becomes a new shell; after this it becomes a visible choice. That is the honest behaviour, and it is the price of never resuming an agent twice — but it is your call, not a technical detail.
