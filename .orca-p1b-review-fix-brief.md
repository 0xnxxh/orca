## Issue 1 — BUG (must fix): admitted overflow markers lost on setWrite / failed settlement
**File:** `src/relay/relay-watcher-event-emitter.ts` (`publishOverflowMarker`)

### Bug
`publishOverflowMarker` only retains markers when admission rejects (`accepted === false && !settled`). Once a marker is **admitted**, the settlement callback only clears `inFlight` and ignores `result.ok`.

On `RelayDispatcher.setWrite()`:
1. old writer is closed
2. queued + in-flight control frames settle `ok: false` (see `dispatcher-client-writer.ts` `close`)
3. `inFlight` is cleared; nothing moves to `pending`
4. `notifyClientCapacity()` only flushes `pending`
→ **admitted-but-undelivered overflow is silently dropped** → remote tree can stay desynced.

Existing test `republishes a retained marker against a replaced primary sink` only covers the **queue-full / pending** path, not the **admitted-then-dropped** path.

### Fix requirements
- On settlement `ok: false`, re-retain the overflow for that root so it can be republished when capacity returns / after sink replace.
- **Timing pitfall:** `setWrite` sets `primaryClient.closed = true` *before* `writer.close()`, so a naive “retain only if client is open” check will still drop during replace. Prefer retain-on-fail and let `onClientDetached` / `forgetClientMarkers` clear real detaches (verify detach order: settlement then detach forget).
- Do not re-send after successful write.
- Do not leak slots or double-send on re-entrant flushes.
- **Regression test:** admit one overflow into a **non-full** control queue against a stalled sink (so it is in-flight/admitted, not pending), then call `setWrite` with a replacement sink; expect the replacement sink to receive the overflow marker.

## Issue 4 — SUGGESTION (perf): pending overflow flush thrash under dual-queue pressure
**File:** `src/relay/relay-watcher-event-emitter.ts` / dispatcher capacity notifications

While any overflow is pending, every writer capacity notification (including ordinary/producer settlements) runs `flushPendingOverflowMarkers`, re-attempting every pending root. Under dual-queue pressure where control lane stays full, this is repeated failed re-admits proportional to producer traffic.

### Fix
Gate flush on control-lane headroom **or** track that control was full and only flush after control-frame release / real control capacity; optional microtask coalesce. Must not break the existing admission-reject retry tests or setWrite republish.

If you need a small dispatcher API (e.g. control headroom probe), keep it minimal and well-named — no vague helpers/utils modules.
